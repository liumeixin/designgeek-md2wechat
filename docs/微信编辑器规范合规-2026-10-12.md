## 二、问题 1：`text-align` 使用了非标准值（用户主诉）

### 根因

`frontend/index.html` 的 `copyHtml()` 会把 `getComputedStyle()` 的结果**逐个属性内联**。
而按 CSS 规范，`text-align` 的**初始值就是 `start`**（逻辑值）——
Chromium 对未显式设置对齐的元素，`getComputedStyle(el).textAlign` 返回的正是 `"start"`。

实测（Chromium 1243）：

```
getComputedStyle(document.querySelector('#wenyan p')).textAlign  →  "start"
```

主题里只有 `h1/h2` 等少数元素显式写了 `text-align`，其余 `p / li / blockquote / td / code …`
全部落进这个坑，于是导出 HTML 里塞满了 `text-align:start`。

规范 §1.6 原文：

> **错误场景**：设置 `text-align` 为 `start`，`end`
> **影响说明**：不同终端对 `start` 值兼容性存在差异，造成部分设备文字居中、
> 部分设备文字居左的不一致体验。

### 修复

在 `copyHtml()` 内联前加一道取值归一化：

- `start → left`、`end → right`、`match-parent → left`
- 只放行 `left / center / right / justify`，其余一律丢弃

同时把「计算值 = 属性初始值」的无效声明一并丢掉（见问题 3）。

## 三、问题 2：正文内联了 `font-family`（规范 §3）

规范 §3「字体使用规范」核心原则：

> **不建议设置任何字体族（font-family）**。公众号已设定一套经过充分优化的默认字体栈……

原实现把字体栈内联到了**每一个元素**（`font-family` 出现 50+ 次/篇），
且外层 `<section>` 还硬编码了 `-apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`。

**修复**：正文一律不输出 `font-family`，交给平台默认字体栈。
仅保留**与正文字体不同**的声明（实际就是 `code / pre` 的等宽字体，属功能性例外）。

> ⚠️ 可见变化：伪元素装饰（如引用块的大引号 `"`）原本指定了 `font-family: serif`，
> 现在改用平台默认字体，字形略有变化。如需保留原字形请告知。

## 四、问题 3：内联样式噪音（体积与可维护性）

`getComputedStyle` 会把「等于初始值」的无效声明也吐出来，原实现照单全收。实测一个 `<p>`：

```html
<p style="color:rgb(85,85,85);font-size:16.15px;…;text-align:start;
  background-image:none;background-size:auto;background-repeat:repeat;
  background-position:0% 0%;background-attachment:scroll;
  border:0px none rgb(85,85,85);border-left:0px none rgb(85,85,85);
  border-top:…;border-right:…;border-bottom:…;
  border-color:…;border-left-color:…;border-style:none;
  box-shadow:none;opacity:1;…">      ← 约 700 字符
```

**修复**：新增 no-op 丢弃表（`background-*` 初值、`border*: 0px none`、`box-shadow:none`、
`opacity:1`、`vertical-align:baseline`、`letter-spacing:normal`、`text-decoration:none` …），
并移除 `border-color / border-style / border-left-color` 三个冗余长写（已由 `border` 简写覆盖）。

同一个 `<p>` 现在：

```html
<p style="color:rgb(85,85,85);font-size:16.15px;font-weight:400;font-style:normal;
  letter-spacing:0.5px;text-align:left;list-style-type:disc;">   ← 131 字符
```

## 五、问题 4：伪元素 `content: url(data:image/svg+xml,…)` 被当正文文字输出 ⚠️

**这是本次发现的既有严重缺陷，不是本次改动引入的**（已用 `git show HEAD` 的原始版本
在真实浏览器中复现比对，两版均为 2 处）。

`injectPseudoElements()` 用 `/url\(["']?([^"')]+)["']?\)/` 提取 `content` 里的图片地址。
字符类 `[^"')]` **排除了 `)`**，而 SVG data-URI 内部几乎必然含 `)`（`translate(-50%)`、
`rgba(...)`、`Q15 85 1…` 等）。于是正则截断/失配 → 走进「当文本处理」分支 →
**把整条 data-URI 原样输出为正文文字**。

影响面（修复前）：

| 主题 | 裸 data-URI 文本出现次数 |
|---|---|
| `sunrise` / `winter` | 58 / 58 |
| `cli` | 49 |
| `fireworks` | 6 |
| `color-pop` / `newyear` | 4 |
| `cyber` / `girl-pink` / `grass` / `lavender-purple` | 2 |
| **合计** | **187** |

渲染出来就是一大段 `url("data:image/svg+xml,%3Csvg…")` 字符糊在正文里（见 `grass` 主题截图）。

**修复**：改为按引号配对取值 `/url\(\s*(?:"([^"]*)"|'([^']*)'|([^)]*))\s*\)/`；
并加兜底——只要 `content` 里含 `url(` 却解析失败，就**跳过该伪元素**，
绝不把原始 URI 当文字输出。

修复后裸 data-URI 文本 **187 → 0**。

> **顺带修掉的同源问题**：`bgInline` 把主题 `#wenyan` 的 `background-image: url("data:…")`
> 原样拼进外层 `<section style="…">`，其中**未转义的 `"` 会提前闭合 style 属性**，
> 导致该属性后半段（含 `color` / `padding`）被浏览器丢弃——20 个主题里有 **8 个**中招
> （color-pop / cyber / fireworks / girl-pink / grass / lavender-purple / sunrise / winter），
> 本次新增的 §4.1.1 容器 `color` 也因此失效。
> 已改为 `m[1].trim().replace(/"/g, '&quot;')`，转义后 style 属性不再被截断，
> 20/20 主题的外层 `<section>` 均正确带上 `color` / `padding`。

## 六、§4.1.1 颜色对比度（已按建议修复）

新增的 `scripts/check_wechat_spec.py --contrast` 会沿 DOM 栈累积前景色 /
最近的不透明背景色（`rgba` 会先合成到页面底色），按 WCAG 公式算对比度。

**修复判据**（用户 2026-10-12 拍板「其他都按你的建议修改」）：

1. **正文强调色**：低于 4.5:1 一律提到 4.5:1（与报告初版建议一致）；
2. **同规则前景/背景对**（`color` 与 `background` 写在同一规则里，如序号徽章、行内代码）：
   低于 **3.0:1**（脚本的 error 阈值）且**承载文字内容**的一律修复；
3. **纯装饰**（`hr::before` 的「◆」、幽灵字伪元素、渐变/品牌色徽章）**不动**——
   属视觉设计意图，非可读性缺陷。

### 实际改动（8 处，7 个主题）

| 主题 | 元素 | 前景 / 背景 | 修复前 | 修复后 |
|---|---|---|---|---|

## 七、其他发现与处置

1. **`--sans-serif-font` / `--monospace-font` 从未定义 —— 已删**
   主题 CSS 里 `font-family: var(--sans-serif-font)` 被引用 15 次（`var(--monospace-font)` 10 次），
   但全项目**没有任何一处定义这两个变量**。属「invalid at computed-value time」→ 回退为继承，
   **即主题里的字体设置一直是空转的**。已按建议**删除这 25 处死声明**（无视觉影响，纯清理）。
   涉及 `themes.json` 全部 19 个主题 + `backend/static/css/themes/*.css` +
   `wenyan-data/static/css/themes/*.css`。

2. **`wenyan-editor-docker` 存在完全相同的缺陷 —— 已同步**
   见 §十。

3. **构建链「格式化漂移」—— 已修**
   `python build.py` 原先把 `themes.json` / `dimensions.json` 重写成**压缩单行**，
   而仓库里提交的是 2 空格缩进版，导致每次构建都产生巨大 diff。
   已把 `build.py` 的输出改为 `indent=2`，实测**字节级可复现**（连跑两次 hash 一致）。

4. **`markdown_parser.py`（后端 `/convert-inline` 路径）也设了 `font-family` —— 已移除**
   （仅保留 `code` 的等宽字体）。

5. ⚠️ **`themes.json` 是「双源」结构，改动前必须看清楚**（本次踩到的坑）
   20 个主题里：
   - **15 个**（claude / cli / color-pop / cyber / default / fireworks / girl-pink / grass /
     lavender-purple / macarons / newyear / parrotalk / purple-yellow-pop / sunrise / winter）
     的 `backend/static/css/themes/*.css` 是 **`--wy-*` 变量占位文件**（1513–1581 B，
     且全项目**没有任何 `var(--wy-…)` 消费者**）。`build.py` 因此判定
     「themes.json 里的手工版更长」→ **保留 themes.json**。对这 15 个主题，
     **`frontend/themes.json` 才是真源**。
   - **4 个**（dark-green / notebook-blue / notebook-purple / ugreen）
     的 CSS 是**真文件**，`build.py` 会用 CSS **覆盖** themes.json。
     对这 4 个主题，**CSS 文件才是真源**。

   ⇒ 改主题配色时，**必须先确认目标主题属于哪一类**，否则 `build.py` 会把
   themes.json 的改动悄悄冲掉（本次 `ugreen` 就中招了一次，已改为直接改 CSS 源）。

6. **`grass-nobg` 是坏主题 → 已删除**
   它的 CSS 与 themes.json 条目都只有 `--wy-*` 变量、**没有任何实际样式**
   （上述「CSS 真文件」里它是最短的一个，1519 B）。渲染出来是裸排版。
   **2026-10-12 下午已删除**：CSS 源、`build.py` 显示名、
   `themes.json`/`dimensions.json`/`manifest.json` 全部移除，主题总数 20 → 19。

7. **两个 `.bak` 文件仍在 git 里**
   `frontend/themes.json.bak`（147 847 B，7-29 的旧快照）与
   `frontend/index.html.bak.202607051732`（59 144 B）都是**被 git 跟踪**的历史备份。
   属仓库卫生问题，本次未动（删文件需你确认）。
